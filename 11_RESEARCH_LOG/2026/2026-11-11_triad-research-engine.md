# TriadResearchEngine: one source record across three research views

- **Date:** 2026-11-11.
- **Question:** Can mathematical exploration, source-grounded explanation and an MCP interface share the same research object without duplicating the scientific registry or conflating computed, interpreted and unverified results?
- **Previous formulation:** The interactive atlas already contained 34 public records, 13 canonical objects, source/coverage metadata, four explanatory/local mathematical modules and a separate geometry laboratory. It had no current unified Triad surface or local Microsoft/MCP/Wolfram service boundary.
- **Proposed formulation:** Add a deterministic shared adapter, four fixed experiment contracts and three coordinated views using one selected stable ID. Expose the existing public records through an official-SDK MCP server/App; provide optional bounded Wolfram execution and a Microsoft Agent Framework explanation worker.
- **Reason for change:** Make sources, assumptions, computations and their limits inspectable through multiple interfaces while preserving one public source of truth.

## Scope and continuity

The work is based on commit `8c9308c` on branch `codex/triad-research-engine`. The [Triad overview](../../docs/TRIAD.md) describes its architecture. The public `research.json` supplies all three views; neither the Python worker nor the MCP service maintains a separate copy of the claim registry. All existing research IDs, five epistemic axes, source metadata and protected canonical equations remain unchanged.

The six navigation topics are interface organization, not new scientific objects or promotions. A descriptor binds an experiment only to its explicitly supported mathematical object. Unsupported or philosophical records remain readable without a fabricated calculation. Conversely, a mathematical object lacking an executable binding does not become philosophical merely because no numerical experiment is attached.

## Computation, interpretation and provenance

The four shared JavaScript experiments calculate the unit-ball image/slice, an integer successor/window, a logarithmic reciprocal relation and conditional QFP local-center quantities. Each run carries its input, source revision, method, precision, source assumptions/definitions, output, checks and limitations. The QFP scalar relation stays local; no global metric solution, stability proof or empirical confirmation is introduced.

The browser's local guide is deterministic source presentation. The Microsoft worker's model output, if a provider is explicitly configured and called, remains unverified AI reasoning. No computation tool is available to that worker, and generated prose does not inherit the source record's mathematical verification. Editorial source summaries retain their attribution rather than becoming purported original quotations.

The optional Wolfram adapter accepts only the fixed numeric JSON contract and runs a fixed local script. It has bounded input/output/timeouts and no arbitrary expression-evaluation or cloud fallback interface. Its independent formulas, `Manipulate` views and SVG/PNG export scripts are implemented but have not executed on this host because no runtime was found within bounded discovery. No comparative output or generated Wolfram graphic is fabricated.

Experiment import recomputes the current JavaScript result and requires matching source and exact JSON values. This guards against edited evidence but has a documented floating-point portability limitation: small implementation-dependent final-bit changes may cause rejection. The deterministic source fingerprint is not a cryptographic signature, authorship claim or proof of scientific validity.

## Consequences and unresolved work

- Multiple research interfaces can retrieve the same stable object and preserve its classification axes, domain and dependencies.
- Real bounded JavaScript experiments produce inspectable result records; mathematical teaching constructions remain separate from physical hypotheses.
- Local MCP transport/App verification establishes implementation behavior, not production registration or scientific validity.
- A usable Wolfram installation and an explicitly configured provider are still required for their corresponding real execution checks. Optional service failure must stay visible rather than being replaced with a claimed success.
- Presentation review produced clear configured-versus-tested status, original-versus-editorial attribution and visible local-domain warnings before the final passing built-browser run.
- Full QFP metric reduction, global existence/uniqueness, boundary conditions, stability, observational discrimination and unresolved historical-source recovery remain independent research tasks.

No canonical epistemic status is promoted by this software integration. Previous atlas and mathematical-review records retain their own provenance and verification boundaries.
